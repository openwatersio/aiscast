# client

The web client for aiscast at `openwaters.io/ais/`: a live map with vessel and station pages, search, and track playback. React Router in framework mode on a Cloudflare Worker, so `/ais/vessels/:mmsi` and `/ais/stations/:id` are server-rendered and can be shared and indexed. It is a client of the aiscast API like any other.

```sh
npm install                      # from the repo root; client/ is a workspace
npm run dev -w client            # http://localhost:5173/ais/vessels, rendering in workerd
npm test -w client               # unit tests
npm run test:e2e -w client       # browser tests, against a local aiscast server
npm run typecheck -w client      # generates the Worker and route types, then tsc
npm run build -w client
npm run preview -w client        # the built Worker, locally
```

`AIS_API` in [wrangler.jsonc](wrangler.jsonc) is the API the server renders against, and the root loader hands it to the browser, so pointing the app at a local server is one setting. Put `AIS_API=http://localhost:8080` in `client/.dev.vars` to override it locally. `AIS_TOKEN`, a secret set with `wrangler secret put AIS_TOKEN`, is a partner token that gives server renders its limits, such as the longer track. Minted with an `rpm` claim (`aiscast-key new … -rpm <n>`), it also gives them their own HTTP request budget; without one, renders share the per-address limit of the Worker's egress addresses.

## Routes

`/ais/vessels` is the map and search, `/ais/vessels/:mmsi-:name` a vessel, `/ais/stations` the station list, `/ais/stations/:id` a station, and `/ais/network` what the network is receiving and where it hears vessels. While the network page is open the map draws `/v1/coverage/tiles` in place of the vessels, colored by vessels a day, and while the station list is open it draws the same tiles colored by how many stations heard each cell. The MMSI is canonical in a vessel URL and the name slug is cosmetic, so a wrong or missing slug redirects to the canonical form. `?station=<id>` on `/ais/vessels` redirects to the station page, and `/ais/map`, where the map was first published, redirects to `/ais/vessels`. The token page is the website's, at `/ais/token`, and the app reads the token it stores.

`/ais/fleets` lists fleets, collections of notable vessels, and groups of fleets, such as `/ais/fleets/cruise-ships`, as cards with a cover photo. A fleet's page, such as `/ais/fleets/cruise-ships/royal-caribbean`, lists its vessels, sorted and filtered by chips. While it is open, the map rings the vessels shown and frames the whole fleet, as it does search results. Each fleet is a YAML file in [app/fleets/](app/fleets/) and each group a folder, as its README describes. A fleet's own photos, and its vessels', are Commons files it names: the loader asks Commons for them through `namedPhotos` in [lib/media.server.ts](app/lib/media.server.ts) and streams them to the page, so a slow answer never holds the page up. A fleet without photos is headed by its cover vessel's, from the media route. [lib/fleets.server.ts](app/lib/fleets.server.ts) parses them on the server, so the YAML parser stays out of the browser's bundle. Each vessel's last report comes from `/v1/vessels/:mmsi`, one request per vessel, and is kept for a minute so moving between fleets does not spend the address's request limit. A row's age is the vessel's last message of any kind, so it does not date the position. The `/ais/explore` addresses where fleets were first published redirect to their fleets.

`/ais/sitemap.xml` is a sitemap index, built by the Worker in [lib/sitemap.server.ts](app/lib/sitemap.server.ts) and kept at the edge for an hour. It lists `/ais/sitemap-pages.xml`, with the app's pages and every station heard in the last 30 days except volunteers' own receivers, and one `/ais/sitemap-vessels-<n>.xml` for each page of 50,000 vessels that the server's `/sitemap/vessels` answers: ships with a name and a ship's MMSI (nine digits starting 2 to 7), whose position was heard in the last 30 days, each at its canonical address with its last report as `lastmod`. A vessel that has never sent its name is left out, and its page asks not to be indexed.

[wrangler.jsonc](wrangler.jsonc) lists the same top-level paths as the Worker's routes on `openwaters.io`. The website Worker answers everything else under `/ais/`. A new top-level route needs a line in both [app/routes.ts](app/routes.ts) and `wrangler.jsonc`. Built assets are written to `ais/assets/` so the assets binding serves them at the path they are linked from. The whole route manifest ships with the first page, because lazy route discovery would ask `/ais/__manifest`, a path the website owns.

## How it works

Each route has a server `loader` for a document request and a `clientLoader` for navigation inside the app. The client loader calls the API from the browser with the visitor's token, so after the first page the Worker is not involved. A vessel the stream has already heard opens from the stream's copy while the record loads.

The map, the stream, and the vessel cache are built once in [components/Shell.tsx](app/components/Shell.tsx) and outlive every navigation, because the stream is capped at two connections per network address and remounting would spend that budget. For the same reason the tabs of one browser share one stream. [lib/streamHub.ts](app/lib/streamHub.ts) holds the socket in a SharedWorker, subscribes to the union of what the tabs are looking at within the key's limits, and passes each tab the events in its own view. When the views do not all fit within the key's area cap and its limit on followed vessels, visible tabs come first, then the most recently focused. A tab that does not fit gets none of its view and shows "Live in another tab" while the tiles carry it. The tabs also share the stream's message rate. A browser without SharedWorker runs the same hub in each tab, with a stream per tab. One panel floats over the map, a bottom sheet on a phone, and camera padding is measured from it, so a selected vessel centres in the part of the map you can see. The panel is one navigation stack. Back from vessels opened one after another on the map returns to the page they were opened over, while the browser's own back steps through each.

The Worker keeps each vessel and station page at the edge for a minute, one copy per theme, so a crawler's second visit, or a link shared to many people at once, costs the API nothing. No page renders anything about the visitor beyond their theme. The Worker writes where their network address places them into each page's head on its way out, after the edge cache, and the map opens there unless the address has a `#map=` hash. A vessel or station page opens on its vessel or station instead: a camera move asked for before the map's first render jumps rather than flies. Browsers are told to keep nothing, so a theme switch shows on the next load.

[lib/map.client.ts](app/lib/map.client.ts) is browser-only, which keeps MapLibre out of the Worker. The vector tiles from `/v1/vessels/tiles` draw every vessel's last known position at every zoom. They reload when a pan starts, when the stream lets go of a vessel still in view, and every five minutes, or every 15 seconds past the stream's area cap, where nothing else updates them. Within the stream's area cap, `/v1/stream` draws the vessels it hears on top, and each one's tile copy is hidden with feature state so no vessel is drawn twice. The subscription asks for no snapshot: the tiles paint the starting picture and the stream says what changes. Triangles point along heading, falling back to course; colour is ship-type class; opacity fades with age, the same for both sources. The viewer extrapolates nothing: it draws a vessel where that vessel last reported. In dev builds and the browser tests' build the map is on `window.aiscastMap`.

The design system is Tailwind utilities over the tokens in [app.css](app/app.css), and the shared components in [components/ui/](app/components/ui/). A component never names a CSS variable, and `npm run check:styles` fails CI if one does.

## Browser tests

[e2e/](e2e/) runs the app in Chromium with Playwright: the phone sheet on an emulated iPhone, back navigation, the one map and stream through a navigation loop, tabs sharing one stream, the server-rendered pages, and vessels drawn once between the tiles and the stream. [e2e/server.sh](e2e/server.sh) starts the aiscast server, fed by Digitraffic alone, and builds it first unless `AISCAST_BIN` names one. The app is built for wrangler's `e2e` environment, which renders against that server, and served by `vite preview`. Each run picks free ports for the server, its UDP listener, and the app, so worktrees can run the tests side by side. A second run in the same worktree stops at startup, because runs there share the build and the server's state. Set all three of `AISCAST_E2E_API_PORT`, `AISCAST_E2E_UDP_PORT`, and `AISCAST_E2E_APP_PORT` to pin them. Run `npx playwright install chromium` once.

The data is Digitraffic's live feed, so the tests look up the vessels they open rather than naming them. A server that starts empty knows few vessel names at first, because names come with static data every few minutes, and the run waits until it has some. The server keeps its state in `e2e/.run`, so the next local run starts with the vessels the last one heard. Each run mints a partner token for the server, the Worker and the browser, because every request comes from one address and would otherwise run into its rate limit. A stream opened in a SharedWorker is out of Playwright's sight, so the tests that count streams give each browser a token of its own that the server lets hold one stream, and a second would show as refused. The basemap is replaced with a blank style.

## Vessel pages

`/ais/vessels/media/:key` answers a vessel's photos as JSON, from [lib/media.server.ts](app/lib/media.server.ts). The key is a 7-digit IMO, checked against its check digit, or for a vessel without one a ship's 9-digit MMSI. Photos are the newest eight in Wikimedia Commons' `Category:IMO <n>` and its first ship-name subcategories, or `Category:MMSI <n>`. For an IMO, the photo the ship's Wikidata item names (P18) comes first, whether or not the category holds it. Editors choose that photo for the hull, while categories are filed by hand and sometimes hold another ship of the same name. The Worker asks Wikimedia with a User-Agent naming a contact, as its API policy requires, and caches the answer at the edge for a week, a day when there is nothing, and 15 minutes after an upstream failure, including a Wikidata failure that leaves the photos without their lead. The browser hotlinks the 960px thumbnail the API returns, or the 120px one in search results; both are standard Wikimedia widths, which render freely. Every photo shows its credit, `© artist · licence`, linking to the file page and the licence. A document render uses the first photo as `og:image` when it comes within a second.

The vessel page's particulars come with the vessel from `/v1/vessels/{mmsi}`, which the server syncs from Wikidata and, for US-flag vessels, the Coast Guard's PSIX.

The drawing in [components/ui/ShipDiagram.tsx](app/components/ui/ShipDiagram.tsx) is a silhouette for the vessel's ITU type, stretched to its length and beam with the drawn ratio kept between 2:1 and 6:1. The antenna's offsets are read by ITU-R M.1371's rules in `vesselDimensions()` in [lib/ais.ts](app/lib/ais.ts): 511 and 63 mean "that many metres or more", so the size is unknown and nothing is drawn; a zero offset means the reference point is not available, so the hull is drawn without the antenna. The offsets come from the API's `to_bow`, `to_stern`, `to_port` and `to_starboard`, or from the stream's static data.

## Share cards

Pages name a 1200×630 PNG as their `og:image`, so a shared link unfurls with what the page is about. `/ais/stations/<id>.png` is a station's: its title, what it is and where, and its vessels and unique vessels over 24 hours. `/ais/vessels/<mmsi>.png` is a vessel's, which its page uses unless a Wikimedia photo comes back within the second the render waits for one: its name, class and flag, and its size, year built, voyage draught, or numbers, nothing that changes by the minute, since a card is kept for an hour. `/ais/network.png` and `/ais/stations.png` show the network's and the station list's last 24 hours, where stations are the volunteer receivers and feeds are counted apart. `/ais/fleets/<id>.png` is a fleet's or a group's, and `/ais/fleets.png` the Fleets page's: its title, its summary's first sentence and how many vessels, or fleets and vessels, over its cover photo from Wikimedia Commons, or over the map when it has none or Commons does not answer within a few seconds. The Worker answers them before the app, from [lib/shareCard.server.tsx](app/lib/shareCard.server.tsx), a station's with its row from `/v1/stations`, and keeps each at the edge for an hour, or five minutes for a station or vessel the API does not know, by its canonical path, so every spelling of a station's id or a vessel's MMSI shares one card. A station that sent messages but reads 0 vessels has no counts to show: it connected minutes ago, the server has no ClickHouse or cannot read it, or it is a boat that hears only itself, whose own ship the counts leave out. Its card and its page's description show its messages instead, and while no station has counts the station list's card leaves its vessels out, rather than show 0 for an hour. An empty station list, as in the seconds after the server starts, is answered as an outage, which is not kept, by every card drawn from it. No station id ends in `.png`, because the server refuses a token subject that does, so a card's address never shadows a page. It renders with workers-og, which loads its wasm only when a card is asked for, in Inter from `@fontsource/inter`, Latin and Latin Extended only, so a name in another script shows as boxes. A page with no card shares the default one, `openwaters.io/og/ais.png`.

## Tracks

A vessel's Track section shows the last 6 hours to 30 days, or pages back through its history one period at a time. Past pages end on UTC boundaries, so a page is a quarter, half, or whole day, whole days for the 48-hour and 7-day ranges, and a calendar month for the longest. Past 30 days the server answers at one position per 15 minutes at most. The server spreads the token's position limit over the range. Every tier reaches a vessel's whole history, and paging back stops at the vessel's first sighting. A past range stands alone on the map, without the stream's live positions joined to it, and the map frames it when it loads. The GPX download covers the range on screen and is fetched with the visitor's token when there is one.

## Search

Search starts when the field takes focus and ends at its clear button or Escape. It does not end when the field loses focus, which a tap on a chip or a scroll of the list does. With nothing typed, it lists the vessels on the map from `/v1/vessels?bbox=`, updated from the stream, the 50 nearest the middle of the map shown. Search asks `/v1/vessels?q=` and keeps the results it last showed until the server answers, so the list changes once per answer rather than with each key pressed. The Where chip chooses Anywhere, In this view, or Near me. Results are ordered by distance, sent as `around=`, from the middle of the map, or with Near me from the reader's position, which the browser is asked for only then, so of many boats with one name the nearest comes first. In this view adds the map's `bbox=`, and past the reader's area cap asks them to zoom in instead. With nothing typed, Near me moves the map to the reader. A Heard window orders results by when they were last heard instead. The list is ranked on the server's answer and then updated from the stream, so a vessel reporting does not reorder it. The Type and Heard chips add `type=` and `max_age=` from [lib/searchFilters.ts](app/lib/searchFilters.ts): Heard's windows start at local midnight, the start of the week in the reader's locale, the month, or the year, sent as seconds to now, rounded to the minute. Each row shows the town the server places the vessel near, its type and length, its distance from the middle of the map, and its speed when under way. While the list shows, each result is ringed on the map, and pointing at a row brightens its ring. Result rows ask for photos only once they have been on screen.

## Errors

The browser reports errors to the Worker at `/ais/errors` with `navigator.sendBeacon`, from [lib/report.ts](app/lib/report.ts). It reports uncaught errors, unhandled rejections, errors that reach a route's error boundary, a basemap that fails before its style loads, a lost WebGL context, and a stream that closes five times in a row without a welcome or sends an error the app does not expect. Half of page loads report, each at most five distinct errors. A report holds the error's name, message and stack, and the first two segments of the path, such as `/ais/vessels/*`. Query strings, fragments, tokens, email addresses, tile coordinates and other coordinates are removed before it is sent, and again by the Worker, in [lib/report.server.ts](app/lib/report.server.ts). The Worker adds the browser's user agent and logs at most 60 reports a minute per isolate. Workers Logs also keeps its own record of every request to the Worker, these included.

Server errors are logged the same way, from `handleError` and the render's `onError` in [entry.server.tsx](app/entry.server.tsx). Each is one `console.error` of an object with `event: "app_error"`, `source` (`browser` or `server`), `kind`, `name`, `message`, `stack`, `path`, and for browser reports `ua`. To read them, open the `aiscast-web` Worker's Observability tab in the Cloudflare dashboard, filter on `event` equal to `app_error`, and group by `kind` or `message`. `npx wrangler tail aiscast-web --format json` shows them live.

## Deploy

Cloudflare Workers Builds deploys the `aiscast-web` Worker from `main` and uploads a preview version for every other branch, with a preview URL on the pull request. It builds from the repo root, where the workspace's lockfile is, with `npm run build -w client`, then runs `npx wrangler deploy --cwd client`, or `npx wrangler versions upload --cwd client` for a branch. The build writes the Worker's generated config, which wrangler finds from `client/`. Only changes under `client/` trigger a build. `npm run deploy` in `client/` does the same by hand.
