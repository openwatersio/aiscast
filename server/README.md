# aiscast server

AIS ingest → reassemble → dedupe → decode → bbox fan-out, with an aisstream.io-compatible WebSocket at `/v0/stream`. One Go binary. See [docs/architecture.md](../docs/architecture.md) for the design.

```sh
ALLOW_ANON=1 go run .          # Kystverket upstream on, HTTP :8080, UDP :10110, archive/ in cwd; no tokens needed
go test ./...
```

[openwaters.io/api/ais](https://openwaters.io/api/ais/) documents the endpoints. `/mcp` is the MCP (Model Context Protocol) endpoint for AI assistants: Streamable HTTP, stateless, six read-only tools over the vessel cache, the vessel record, tracks, and station stats (`mcp.go`, `track_api.go`), the same claims and rate limit as `/v1/vessels`. `server.json` at the repo root is its registry listing; its version and `mcpVersion` move together. Operator-only: `GET /metrics` serves Prometheus text (events, duplicates, parse/decode failures, client drops, rate-limit rejections, unmapped source fields and record types, vessels, open streams by protocol and tier, fan-out sends and bytes, HTTP requests by route and status with latency histograms for the vessel routes and `/mcp`, per-source event counts, last-event age, and delay percentiles, archive and access log upload failures and staged bytes, access log lines dropped, `aiscast_build_info` with the git revision of the binary, the standard `process_` series, and the garbage collector's CPU, cycles, allocations, and live heap as `go_gc_cpu_seconds_total`, `go_gc_cycles_total`, `go_heap_allocs_bytes_total`, and `go_heap_live_bytes`). The alert rules and dashboard in [deploy/grafana/](deploy/grafana/) query these names.

Environment:

- `ADDR` (`:8080`), `UDP_ADDR` (`:10110`): comma-separated UDP listeners as `[label=]host:port`, labels unique. `/metrics` counts datagrams per label, so a listener per address shows which name feeders send to.
- `KYSTVERKET` (`1`), `KYSTVERKET_ADDR`.
- `BARENTSWATCH_CLIENT_ID` + `BARENTSWATCH_CLIENT_SECRET` (set = BarentsWatch upstream on), `BARENTSWATCH_URL`.
- `DIGITRAFFIC` (`1`), `DIGITRAFFIC_URL`.
- `AISSTREAM_API_KEY` (set = aisstream.io upstream on), `AISSTREAM_BBOX` (world), `AISSTREAM_URL`.
- `AISHUB_FEED` (`data.aishub.net:<port>`): forward volunteer-station events to AISHub as plain `!AIVDM`. The server never forwards public feeds or synthesized events, per their terms.
- `AISHUB_USERNAME` (set = poll AISHub's aggregate snapshot), `AISHUB_INTERVAL` (`20s`, the limit AISHub set for our account).
- `ARCHIVE_DIR` (`archive`).
- `ACCESS_DIR` (`access`) + `ACCESS_BUCKET`: the access log, one JSON line per HTTP request, staged in hourly gzip files and uploaded under `access/v1/` to `ACCESS_BUCKET` with the R2 credentials. `off` turns it off. Without a bucket the hours stay on disk, and the sweep uploads them once one is set. See [Access log](#access-log).
- `DEDUPE` (`dedupe.json`): the dedupe window, saved on shutdown and restored on boot so a restart cannot re-accept a copy inside the 10 s window.
- `R2_BUCKET` + `R2_ACCOUNT_ID` + `R2_ACCESS_KEY_ID` + `R2_SECRET_ACCESS_KEY`: unset = archive stays local. Otherwise the server PUTs each hour to R2 over the S3 API on rotation. Shutdown closes the open hours without uploading them, so a restart takes seconds, and the next process's sweep uploads them at boot. `aiscast sweep` runs that sweep once and exits, for a box whose server will not start again. Use `S3_ENDPOINT`/`S3_REGION` for non-R2 targets.
- `ISSUER_PUBKEYS` (`kid:base64url-pubkey,...`): the issuers whose tokens aiscast accepts.
- `PERSONAL_ISSUER_KEY` (`kid:base64url-seed`): lets `POST /v1/keys` mint personal-tier tokens.
- `REVOKED_SUBS` (comma list).
- `LOCKED_STATIONS` (comma list of station ids): moderation. A locked station shows no operator or vessel name and refuses new names, and keeps publishing.
- `ALLOW_ANON=1`: no tokens needed, local development only.
- `USAGE` (`vessels-usage.json`): the rolling 24 h/7 d counters behind `/v1/stats`, written every minute and on shutdown, and restored on boot.
- `STORE` (`aiscast.db`): the vessel record, in SQLite. The vessel cache is restored from it on boot. `off` runs without it, and a restart starts with an empty map. It also holds the `stations` table: names, coverage labels, and which keys must sign their token requests. A signed request is saved there before its token is issued, so without the record those locks last only as long as the process. See [Vessel record](#vessel-record).
- `WIKIDATA` (`1`): sync vessel particulars from Wikidata weekly into the vessel record. `0` turns it off. `WIKIDATA_URL` (`https://query.wikidata.org/sparql`) names the query endpoint. See [Vessel particulars](#vessel-particulars).
- `USCG` (`1`): list US-flag vessels from the Coast Guard's PSIX weekly and read dimensions and tonnage for the ones AIS matches. `0` turns it off. `USCG_URL` (`https://cgmix.uscg.mil/xml/PSIXData.asmx`) names the SOAP endpoint. See [Vessel particulars](#vessel-particulars).
- `FISKERIDIR` (`1`): sync Norway's fishing vessel register weekly. `0` turns it off. `FISKERIDIR_URL` (`https://api.fiskeridir.no/vessel-api/api/v1/vessels`) names the endpoint. See [Vessel particulars](#vessel-particulars).
- `FCC` (`1`): sync active FCC ship station licenses weekly from the ULS bulk files. `0` turns it off. `FCC_URL` (`https://data.fcc.gov/download/pub/uls/complete/l_ship.zip`) names the download. See [Vessel particulars](#vessel-particulars).
- `TC` (`1`): sync Transport Canada's Register of Large Vessels weekly. `0` turns it off. `TC_URL` (`https://opendatatc.tc.canada.ca/large-vessel-registry_dataset_en.xlsx`) names the download. See [Vessel particulars](#vessel-particulars).
- `ISED` (`1`): ask ISED's Canadian MMSI registry about heard CA-flag vessels, on demand. `0` turns it off. `ISED_URL` (`https://ised-isde.canada.ca/mmsi-ismm/api/ship`) names the endpoint. See [Vessel particulars](#vessel-particulars).
- `CLICKHOUSE_URL` (`clickhouse://127.0.0.1:9000`, set = write every copy of every position report to ClickHouse on the box): the server creates the `aiscast` database, or the one the URL names, with `receptions`, the `positions` view over it, and `positions_1m`, each vessel's track at a position a minute while it moves and a heartbeat every 30 minutes for each place it sits still. The schema moves forward in numbered steps, each recorded in `schema_migrations` and run once at start. A step only adds a table, a column, or a view, so a server from before a step still writes after it, and rolling back a deploy never stops history. No step renames a table, since a materialized view stays on the table it was created over. Anything that drops or rewrites data runs only by hand: `aiscast convert-receptions` rewrites the rows `receptions` holds from its first layout, which named a transmission by a 64-bit `tx` and kept `recv_ts`, a day at a time in place through the live writer's own code, and can be rerun; `aiscast clickhouse-cleanup`, once every day is converted, drops `positions_15m`, `positions_1h`, and `positions_old`, which only a server from before the current layout reads, and the first layout's rows and columns, after which a server from before the current layout can no longer write. It connects in the background and retries each minute, writes once a second, and never holds up ingest: a full queue drops its oldest copies and counts them in `/metrics`. Tracks read from it; without it they answer 503. See [Tracks](#tracks). Receptions before 2026-10-03 23:38 UTC came from the lake: every transmission the stream accepted and every copy dedupe matched to one, but not the stale and implausible events the stream withheld, which the lake never held.
- `MARINECADASTRE` (set = load the U.S. Coast Guard's Nationwide AIS archive from MarineCadastre into ClickHouse; needs `CLICKHOUSE_URL`), `MARINECADASTRE_FROM` (`2025-10-01`, the first day to load), `DMA` (set = load the Danish Maritime Authority's AIS archive the same way), `DMA_FROM` (`2025-10-01`), `CLICKHOUSE_LOADER_URL` (required for archives to load, such as `clickhouse://loader@127.0.0.1:9000/aiscast`: the connection archive loads use, as the `loader` user, whose settings profile keeps a load within the memory, threads, and priority the live writer can spare; without it, or naming another database than `CLICKHOUSE_URL`, archives do not load. The user is granted the `aiscast` database; a deployment with another changes the grant in [loader.xml](deploy/rootfs/etc/clickhouse-server/users.d/loader.xml)). See [Historical archives](#historical-archives).
- `WS_CONNECTS_PER_MIN` (`60` per IP).
- `STATION_SALT`: keys the UDP station ids and the access log's client hashes. Set it on a public host.
- `TRUST_CF_HEADERS=1`: use it only when Cloudflare proxies the hostname. It makes rate limits key on `CF-Connecting-IP`.
- `PPROF_ADDR` (`127.0.0.1:6060`): serves `net/http/pprof` on this address, never on `ADDR`. `off` turns it off.

## Access tokens

Every credential is an Ed25519-signed claims token, `ak1.<claims>.<sig>`. You mint it offline with `go run ./cmd/aiscast-key`, and aiscast verifies it with the issuer's public key. aiscast holds no key that can mint more than personal-tier tokens.

Claims:

- `sub`: station id, partner, or device key.
- `role`: `personal` subscribes and publishes as the device key with small limits, `feeder` publishes, `peer` publishes and subscribes, `partner` subscribes, `admin` does all.
- `exp`.
- optional `bbox`: subscriptions must fit inside it.
- `cidr`: source addresses.
- `conns`: concurrent WebSockets.
- `rate`: messages/s per connection, excess thinned.
- `area`: total subscribed square degrees.

`tiers.go` holds the defaults, and [docs/limits.md](../docs/limits.md) documents them: anonymous 2 per address / 20 / 100 (subscribe only), personal 2 / 50 / 400 with no expiry, feeder 5 / 200 / unlimited plus `/v1/nmea`. A personal token earns the feeder tier when its stations deliver 1,000 events in 24 h. You can also mint a feeder token directly. The cap is 8 streams per address across tokens.

The token goes everywhere an API key went: aisstream `APIKey`, `Authorization: Bearer`, Basic-auth password (AIS-catcher `USERPWD x:ak1...`), MQTT CONNECT password (AIS-catcher `-Q wssmqtt://x:ak1...@`), or `?key=`. A browser page on another origin can send the header too: every JSON endpoint answers the CORS preflight, so a token never has to go on the query string. `POST /v1/keys {"pubkey": "<base64url ed25519 public key>", "ts": <unix seconds>, "sig": "<signature>"}` returns a personal token (no expiry) for that device key. `sig` signs the request with the key, so nobody else can mint a token for a station; once a key has signed, unsigned requests for it are refused, and a request that names the station must be signed. The signed lines and an `openssl` recipe are in [openapi.json](openapi.json). The Signal K plugin and the chart plugin use this, and they bundle no secret. `/v1/stream` subscribe and `/v1/vessels` are open. `/v0/stream`, publishing, and `/v1/receive` need a token.

`aiscast-key issuer` makes an issuer keypair. `aiscast-key new -sub station-42 -role feeder -exp 8760h` mints a token. `aiscast-key inspect <token>` shows the claims.

Sources:

- Kystverket (Norway, NLOD, TCP NMEA).
- BarentsWatch when `BARENTSWATCH_CLIENT_ID` is set (Norway, NLOD, JSON stream, `synthesized`). The same AIS Norge network as Kystverket plus satellite and offshore receivers out to the EEZ and Svalbard. Events rebuilt from a non-NMEA source must advance the vessel's clock, so its copies of transmissions Kystverket already delivered raw are withheld, and it takes over a vessel from that vessel's next missed transmission onward.
- Digitraffic (Finland, CC BY 4.0). The server maps its MQTT JSON to go-ais structs and re-encodes it, and the events carry `synthesized: true`.
- aisstream.io when `AISSTREAM_API_KEY` is set. The server maps its `/v0` envelopes back to structs, also `synthesized`. Anything the open feeds already delivered dedupes.
- AISHub's aggregate snapshot when `AISHUB_USERNAME` is set (`synthesized`, source `aishub`, reciprocal with `AISHUB_FEED`). AISHub regenerates its world snapshot about once a minute, so positions from it run about a minute behind (`sources.aishub.delay` in `/v1/stats`). The server skips unchanged snapshots.

Volunteer stations feed over `/v1/stream` as MQTT (a socket that negotiates the `mqtt` subprotocol gets a receive-only MQTT 3.1.1 session: the token is the CONNECT password or the request's, each PUBLISH payload is newline-separated NMEA on any topic, QoS 0 to 2 acknowledged, SUBSCRIBE refused), `/v1/receive` (AIS-catcher HTTP output), or `/v1/stream` publish frames. All three name the station by the token's `sub` alone, `station:<sub>`, so a feeder can switch transports without changing identity. UDP senders are `udp:<hash>`, or `mmsi:<n>` once their own `!AIVDO` names the vessel.

Archive layout: `<license>/<source>/YYYY/MM/DD/HH.gz`, one record per line: receive time, station, body as received. A station followed by ` buffered` marks a sender's offline backlog, which live withheld from the stream when stale and replay withholds the same way. A station followed by ` published` marks a line published over `/v1/stream`, which replay feeds to the NMEA parser rather than trying as an AIS-catcher envelope. A record can carry both marks, ` published` first.

## Vector tiles

`GET /v1/vessels/tiles/{z}/{x}/{y}` answers a Mapbox Vector Tile of last known positions with one point layer, `vessels` (`tiles.go`). It answers by the same age rules as `/v1/vessels` (`ageRules` in `vessels.go`): the cache for the last 30 minutes, and the vessel record for vessels last heard up to 7 days ago whose last report was stationary. `/v1/vessels/tiles.json` is its TileJSON and carries its query string, filters and token alike, into the tile URL. The encoder handles points and single-ring polygons and uses the standard library. Tiles are built on demand, the record read first and the cache under its read lock, and gzipped once. A build is shared by every request for the same tile and filters for 10 seconds. Four tiles build at once and the rest wait, so a burst of tiles leaves room for `/v1/vessels`. Past 2,000 vessels a tile keeps the newest in each 8-pixel cell, and a low-zoom tile matches a week of vessels across its area. So the record's vessels are found and thinned in the record mirror, in memory, and only the vessel that wins each cell is copied out. A tile never reads SQLite. The response carries its own `Content-Encoding`, so Caddy passes it through. At 60,000 vessels a z0 tile takes about 20 ms to build and a busy z8 tile under 1 ms. With 300,000 rows in the record, most of them in busy waters, a z0 tile takes about 50 ms, a busy z4 tile about 15 ms, and a busy z8 tile about 3 ms (`BenchmarkTile*`). [openapi.json](openapi.json) documents the properties, the filters, and how clients refresh.

`GET /v1/coverage/tiles/{z}/{x}/{y}` answers the coverage map, where there are vessel positions from any source, with one polygon layer, `coverage`: an H3 cell per feature, with `vessels` (distinct vessels a day, averaged over the window), `days` (days of the window the cell was heard), and `stations` (distinct stations that heard it in the window, each volunteer station counted once whatever streams it tags, and each aggregator and government feed once by its source, whatever receivers or paths it names) (`coveragemap.go`). ClickHouse keeps it in `station_coverage`, each day's distinct vessels per cell and station at resolutions 3 to 6, which a materialized view fills from `receptions` as they are written, skipping implausible and bad-clock copies and anything older than the 13 months it keeps. Its station is the one `receptions` holds, a feed's receiver or path included, except that a volunteer's receptions from before 2026-10-05 15:30 UTC, when ingest began keeping a TAG stream under its receiver, are folded at the first slash. The map merges the stations in each cell, counting a feed's receivers once by its source. `coverage`, the same per cell without the stations named, is still written and rebuilt beside it, so the previous release still has its map on rollback. On first start the server bins the receptions written before each view existed, those loaded from the lake among them, one day and table per query back 13 months, and records each day in `station_coverage_backfilled` and `coverage_backfilled`, so a restart resumes. It bins the map's window first and loads the map, then bins the older days in the background. Distinct sets merge as unions, so every copy of a transmission, and a day the view and the backfill both cover, count each vessel and station once. Replay, an archive day loaded again, and `aiscast rebuild-positions-1m` delete each day they touch from both tables and bin it again. A server rolled back to before `station_coverage` rebuilds only `coverage`, while the view keeps adding to `station_coverage`, so after rolling forward again run `aiscast rebuild-positions-1m` over any day replayed or reloaded in between. Within the server, a backfill's day and an archive reload's rebuild wait for each other; replay and `rebuild-positions-1m` run as commands of their own, so do not run them while the server's first backfill is still binning (its log says when it has binned the days). The server reads the last 7 complete UTC days once ClickHouse connects and every hour after that, with each cell's outline from ClickHouse's H3 functions in the same query. The zoom picks the resolution: 3 below z5, 4 to z6, 5 to z8, 6 above. Tiles are built once per load and served with `max-age=3600`. `/v1/coverage/tiles.json` is its TileJSON and adds the window the tiles cover. Both answer 503 without ClickHouse and until a load finds a day of coverage. With `?station=`, both answer one station's cells over the same window, with `stations` 1 in each and `vessels` averaged over the window's days. The TileJSON's tile URLs carry the parameter, its `bounds` take in every cell it draws at every resolution, and `fit` frames the station with each edge leaving out the farthest 5% of its resolution-6 cells on that side. The server loads a station's cells the first time they are asked for after each hourly load, one station at a time, and keeps stations' cells until the next hourly load, up to four times the network's, dropping others past that. A station that comes back with no cells is served without being kept, and one past that bound on its own is kept alone. Station tiles have a cache apart from the network's. A request waiting for another station's load gives up when its client does, and stations already loaded answer meanwhile. Each load also lists the stations with cells in the window, so a station with none, or an id no station has, answers 404 without a query. A station read while a command such as `rebuild-positions-1m` rebuilds one of its days misses that day until the next hourly load, as the network map does. Coverage tiles share the vessel tiles' rate limit and need no token. In memory a cell is its outline and three counts, about 100 bytes.

## Vessel record

The cache drops a vessel 30 minutes after its last report. The vessel record keeps one row per MMSI ever heard, with its particulars and last known position, in the SQLite file named by `STORE`. It answers what the cache cannot: `GET /v1/vessels/{mmsi}` for any vessel ever heard, a followed MMSI's last position on `/v1/vessels?mmsi=`, the vessels an area on `/v1/vessels` holds past 30 minutes, the `?q=` search, the vector tiles, and the MCP `get_vessels` and `search_vessels_by_name` tools.

`GET /sitemap/vessels` lists the vessels the web client's sitemap points search engines at, in MMSI order and pages of 50,000 (`sitemap.go`): ships with a name and a ship's MMSI (nine digits starting 2 to 7), whose position was heard in the last 30 days. Without `page` it counts each page and gives its newest `seen`; with `page=n` it lists that page. Each answer is one read of the record, kept for 10 minutes, and the web client caches what it builds from them at the edge for an hour. It serves the client, not API users, so it sits outside `/v1` and `openapi.json` leaves it out.

The fold marks each vessel it updates, and a writer upserts the marked vessels once a second in one transaction, so the fold never waits on the disk. The upsert merges with the fold's rules: a vessel that returns after the cache dropped it arrives without its name or position, and a blank field keeps the stored value. On boot the cache is filled with every vessel the record heard in the last 30 minutes, so the record is the one vessel state that survives a restart. `aiscast replay` never attaches the record, so a replayed day cannot overwrite a live position. A record that will not open leaves the server running without it, starting from an empty map that the feeds refill within minutes, and `aiscast_store_up` drops to 0.

History reaches the record from ClickHouse. Once a day, within 15 minutes of an archive load that brought in files, and after a restart when the last import is more than a day old, the server reads every vessel's history a page at a time in MMSI order and merges it ([import.go](import.go)). `positions_1m` gives each vessel's first and last position, the first to within its minute, or 30 minutes while still, and `vessel_statics` an archive's name, call sign, IMO, type, dimensions, draught, and earliest row, so every source in ClickHouse, live or archive, backdates `first_seen` with nothing source-specific here. The import's merge has its own rule, because history is usually older than the record: a stored name or particular is only filled when blank, `first_seen` takes the earlier value, and a position is taken only when it is newer. A vessel only history knows gets a row, with its last position and the source kind that delivered it. An import that finds no history does not count, so it retries at the next check. It runs only with `CLICKHOUSE_URL`, and its queries take two threads and at most 1.5 GB, about 20 seconds a day for 366,000 vessels.

The record mirror holds every row of the record in memory, with the vessels that have a position filed by one-degree cell (`mirror.go`). Lookups by MMSI or IMO, areas past the cache, nearest rankings, counts for `/v1/stats` and the MCP tools, and the vector tiles answer from it, so no request scans SQLite or holds a record connection while it does. SQLite answers only name and MMSI prefix search, substring search, the flag filter that goes with it, and ordering by name, and stays the record of truth. The mirror loads when the record opens, in table order, about 1.5 s and 165 MB for 336,000 vessels. After each write, the flush or a page of a history import, the rows just written are read back and filed again, about 8 ms for a flush of 650, so it follows the record's merge rules at most a write behind. A filed vessel is never changed in place: a refresh files a new one, and readers get copies. A refresh that fails counts in `aiscast_store_mirror_failures_total`, and its vessels are read back again with the next write.

`/metrics` reports `aiscast_store_up`, flushes, flush failures and seconds, rows written, the file size, and the mirror's vessels and failed refreshes. `/metrics` also reports import runs, failures, and rows merged, and when the last import succeeded.

## Vessel particulars

`GET /v1/vessels/{mmsi}` and the MCP `get_vessels` tool serve three properties built by [particulars.go](particulars.go): `particulars`, the vessel's registered facts merged from every source into one vocabulary, metres and tonnes, with no source names in its fields; `provenance`, naming the source of each served field; and `sources`, each contributing source's credit, license, and its own page for the vessel. Merging is per field and deterministic: a flag state outranks Wikidata, an empty value never wins, and a Regulatory or Simplified gross tonnage yields to a Convention figure, with `tonnage_measure` saying how a served flag-state tonnage was measured. A new source adds fields to the vocabulary and a rank to the merge, and no response key is named after it. Where a license asks for credit, NLOD 2.0 and the OGL, the `sources` entry is that credit; none adds a line to `attribution`, which stays the position feed's. The fields are in [openapi.json](openapi.json) under `Particulars` and `SourceRef`.

### Sources

#### Wikidata

For a vessel whose IMO number has an item: ship type, builder and yard number, year built, gross tonnage, deadweight, registered dimensions and design draught, registry and home port, owner and operator, former names, and links to the ship's Wikipedia article and its photos on Wikimedia Commons. About two in three vessels with an IMO have an item. The photos carry their own licenses, so `image` is the photo's page rather than the file.

The particulars live in the `wikidata` table of the vessel record; requests never call Wikidata. Once a week ([wikidata.go](wikidata.go)) the server reads every item with an IMO from the Query Service, about 96,000, one query per field with the labels joined in follow-up queries, since any bigger query runs past the service's 60-second limit. An IMO that fails its check digit is skipped on both sides, an IMO on several items takes the lowest QID, and among several current values for one property a value without an end time wins, then the lowest QID. A sync replaces the table in one transaction and is refused when it loses half the ships, or half of any one field, since each field comes from its own query; a failed sync retries at the next hourly check. `/metrics` reports syncs, failures, the IMO numbers stored, and the last success.

#### US Coast Guard's Port State Information Exchange (PSIX)

For US-flag vessels, a weekly public snapshot of its MISLE database: service type, status, year built, official number, the documented name, registered dimensions, and gross and net tonnage with the system they were measured under.

PSIX has no MMSI and no bulk download, only a SOAP service ([uscg.go](uscg.go)). Once a week the server lists US-flag vessels into the `uscg` table: every vessel with a call sign, plus the call-sign-less vessels whose official number an active FCC license carries, the one join that could reach them. A service the service cannot list whole, as Recreational always was and Commercial Fishing Vessel is now, is listed one build year at a time. A listing is about 250 requests over 15 minutes, replaces the table in one transaction, keeps the dimensions already read, skips `DUPLICATE OF` records, and is refused when it collapses. After each hourly check a backfill reads dimensions and tonnage for matched vessels, a request a second, most recently heard first; three failures in a row end the round.

A vessel matches by call sign and name together. Call signs that cannot be a US one are ignored, and the names must agree: equal after dropping a type prefix such as `F/V` and anything that is not a letter or digit, one a prefix of or inside the other, or a longest common subsequence of 80% of their lengths. That accepts `GOV THOMAS H KEAN` for `GOVERNOR THOMAS H. KEAN` and turns away `WEEKS 551` for `BREAKWATER 551`, a call sign since given to another vessel. Among records that agree, an active one wins, then the newest. An official number from the vessel's FCC license matches a record exactly and skips all of that, though a record only its number reached still needs the names to agree. `/metrics` reports listings, failures, vessels listed, dimension reads, and the last success.

#### Norwegian Directorate of Fisheries

For Norwegian vessels, the open fishing vessel register, under the Norwegian Licence for Open Government Data (NLOD) 2.0: registration mark, build year, registered length and beam, London Convention tonnage, and the owning company. Once a week ([fiskeridir.go](fiskeridir.go)) the server pages all 5,000 or so vessels into the `fiskeridir` table; every row comes complete, so there is no backfill. The register has no MMSI and a third of its rows have no call sign, so a vessel matches as PSIX's do, by call sign and name, among NO-flag vessels. Owners who are people are dropped at sync, so no individual's name is stored or served, and the 1947-measure tonnages with them, so a served figure is always the Convention one.

#### FCC's Universal Licensing System

For US vessels, the full licensing database, published weekly as bulk files in the public domain. Once a week ([fcc.go](fcc.go)) the server downloads the 44 MB ship-service zip and keeps the active licenses that carry an MMSI, about 66,000: the licensed call sign, ship name, and official number, keyed by the MMSI itself, the one join AIS hands us directly. Licensee names are never read. A licensed vessel gets its documented name and official number, and the official number is handed to the PSIX match above. Recreational MMSIs issued by BoatUS and the like are not FCC licenses and are not here, and the license's tonnage and length are not served, since PSIX and Wikidata cover them with clear units.

#### Transport Canada's Register of Large Vessels

For Canadian vessels, a spreadsheet published weekly under the Open Government Licence - Canada: official number, build year, registered dimensions and tonnage, service, and port of registry. The register has no MMSI and no call sign, so once a week ([tc.go](tc.go)) the server keeps the vessels whose IMO has a valid check digit, about 1,200 of its 27,000, and only a CA-flag vessel's IMO looks there, with the names required to agree: an IMO another flag carries now may have left the register, and a mistyped one must not serve another ship's facts. The spreadsheet is a zip of XML the standard library reads, and the register's year column, the year with two implied decimals, is undone and bounds-checked at sync.

#### ISED's National Maritime Information Database

For Canadian vessels, the registry of the MMSIs Canada assigns. ISED serves it publicly one vessel at a time and offers bulk only to the Canadian Coast Guard, so this source loads on demand ([ised.go](ised.go)): after each hourly check a round asks about heard CA-flag vessels never asked about, or not in ninety days, a request a second, most recently heard first, and stores the answer either way, so no vessel is asked about twice in a season. Serving reads only the table. It carries the registered name and call sign, thin but the flag state's own, and for most Canadian small craft the only registered facts any source holds. Crown copyright; the served values are facts, and the per-vessel credit links the public search. `/metrics` reports asks, failures, and the records held.

## Tracks

`GET /v1/vessels/{mmsi}/track` and the MCP `get_vessel_track` tool answer where a vessel has been. They read ClickHouse (`CLICKHOUSE_URL`); without it, track requests answer 503. `aiscast replay` never attaches it.

Every copy of every position report the pipeline receives is written to ClickHouse (`CLICKHOUSE_URL`) as a row of `receptions`, with its station, its arrival time as `recv_delay` after its stamp, and the transmission it carries: the time its accepted copy was stamped, as `tx_off` from the copy's own stamp, almost always 0, and `tx_disc`, one byte of that copy's event id, which tells apart a vessel's transmissions stamped in the same millisecond. Stored that way a reception costs about 11 bytes, where a 64-bit hash and a second timestamp cost 19. A copy dedupe matched by payload names the transmission it matched. A rebuilt copy (AISHub, aisstream, BarentsWatch) never matches a raw payload, and AISHub's arrive a minute late, so each vessel keeps its accepted positions of the last five minutes, and a stale rebuilt copy at one of them, within 4 wire units (about 0.75 m), names that transmission. A stale report that matches none is a real report that arrived late, kept for history though the stream withholds it, once it passes the fold's jump test against the vessel's position nearest it in time; the fold itself never tests a stale report. A stale report from a volunteer station stays out of history: a station's backlog never reaches the fold, so it has no late reports to deliver, and anyone can run one, token or not, and stamp a report into any vessel's past. Late reports come only from the feeds the server pulls. A report judged an impossible jump is kept with `implausible` set, and so are dedupe's later copies of it; one stamped a day or more before it arrived is kept with `clock_bad`. A copy the fold judged older than a report the vessel had already sent, which the stream withholds and the station counts leave out, is kept with `stale`; dedupe's copies are counted as heard and read false, as do rows from before the column. Neither is ever served: the `positions` view leaves out a transmission any copy of which is implausible. The fold and dedupe append each copy to a queue, and a writer sends the queue once a second. With it goes `station_own`: each station's own-ship messages (`!AIVDO`), position and static alike, as the latest per station, hour received, and vessel, kept 35 days, so a station's counts can leave out the boat it is on. The queue holds a few minutes of traffic; past that, a stalled ClickHouse costs the oldest copies, counted in `aiscast_clickhouse_points_dropped_total`, rather than memory. `receptions` keeps every copy, sorted by vessel and time. The `positions` view, which takes the vessel and range as parameters, keeps the copy of each transmission that arrived first, so a source purged from `receptions` leaves its transmissions to the copies other sources delivered.

`positions_1m` fills from each accepted copy as it is written. A vessel is moving when it is more than 50 m from its anchor, where it was last moving; a moving report becomes the anchor. Reported speed does not count: a moored vessel's GPS can report 0.6 to 0.9 kn for days within a few meters, and a vessel leaving at 3 kn passes 50 m in about 30 seconds. Measuring from the anchor rather than the report before catches a vessel drifting slowly, whose reports are each a few meters on. Under 50 m, a moored vessel's GPS jitter and a swing at anchor are noise. The anchor starts at the vessel's last known position, which the vessel cache restores at start. A moving vessel keeps its latest position in each minute; one sitting still keeps one row every 30 minutes for each place it sits, a cell of about a kilometer, its latest report there, a heartbeat that says it was heard there then. The 30 minutes match the live map's, where a vessel heard in the last 30 minutes is active. A range finds a moored vessel in every 30 minutes it overlaps but the last, whose report may fall after the range ends. Its moving rows bound when it arrived and left to the minute. Two thirds of positions are vessels sitting still, so on 2026-10-02 it kept 12.4 M rows of 53 M accepted positions, 2.2 M of them heartbeats, at about 12 bytes a row. Any step of a minute or more groups its rows by the step, so a ferry's track at 15 minutes is its first position in each 15, not a sample that lands at random along its crossings.

`positions_1m` takes each transmission's accepted copy as it is written, and a purge does not move `accepted` to the copy left. So purging a source from `receptions` (`ALTER TABLE aiscast.receptions DELETE WHERE source = '...'`) is followed by `aiscast rebuild-positions-1m -from YYYY-MM-DD -to YYYY-MM-DD` over the days it touched. It rebuilds each day from each transmission's earliest copy, as the `positions` view does, and bins the day's coverage again. Rows the live writer adds meanwhile are kept: `positions_1m` keeps the latest row per window, so the two agree.

`GET /v1/stations` takes each station's `vessels`, `vessels_24h`, `vessels_exclusive_24h`, `uptime_7d`, `positions`, `duplicates`, and its first hour from the station series in ClickHouse (`stationseries.go`), read once a minute. `station_hours` keeps, per station and hour, its usable position receptions and how many were delivered first, for as long as `receptions` keeps them. `station_vessels` keeps, per station, hour, and vessel, its receptions other than stale copies and the time of the latest, for 35 days. A window reads the rows whose latest time falls inside it, and leaves out every row of a vessel the station sent as its own ship within the window, from `station_own`. Both hold counts, so they are rebuilt rather than appended to: a view writes the hour of every reception inserted to `station_dirty`, whatever path inserts it, and every 5 minutes the server deletes each hour marked more than a minute ago since its last rebuild from both tables and bins it again from `receptions`, recording the marker in `station_built`. A day that fails is logged and left for the next run. Markers last 14 days, so a server down or failing for less than that catches up. The figures are up to about 7 minutes behind. Replay, an archive day loaded again, `rebuild-positions-1m`, and a converted day mark the hours their deletes empty. Each run then backfills, newest first and for up to 2 minutes, the days `receptions` held before the view, recording each in `station_series_backfilled`. `/v1/stats` and MCP's `get_coverage` count each source's vessels over the last 30 minutes from `station_vessels`. Without ClickHouse, or once its reads have failed for 10 minutes, those counts are 0, `positions` and `duplicates` count from the last start, and `uptime_7d` is null; a failed read keeps the last figures until then. A volunteer station's place label is the town nearest the median of its resolution-6 coverage cells over 7 days, given at least 5 cells. Its own-vessel candidates are read back from the last two hours of `station_own` at start.

A fix to decoding, dedupe, or staleness changes what the server writes from then on. `aiscast replay -clickhouse` carries it into history, a day at a time, through the code at hand ([replay_clickhouse.go](replay_clickhouse.go)). With `-fetch` it takes each day's raw hours and the lead-in before it from `R2_BUCKET`, about 25 GB a day, and deletes them when the day is done. Before the lead-in it fills the cache, as live's start fills it from the record, with each vessel `positions_1m` has in the 30 minutes before: its last plausible position, its last report from a source that is not low-trust, and its anchor, where it was last moving. Where two vessels share an MMSI, the lead-in then judges plausibility against the one live held, not whichever reported first. It replays the lead-in to build dedupe and corroboration, and writes only the day's copies, into a staging table. It prints the stored and replayed copies per source, and with `-dry-run` stops there. Otherwise it deletes the network's own copies that arrived that day and inserts the replayed ones. Copies from historical archives, the sources in `history_loads`, are never touched, and nor is a copy stamped more than two days from its arrival. It then rebuilds `positions_1m` for the day and the days on either side, and marks an archive's file beside the day whose copies matched the network's transmissions to load again. A replay holding under 90% of the stored copies stops before changing anything, since that usually means missing raw hours; `-force` replaces the day anyway. Only days that ended over a day ago replay, since the live server can still upload a newer copy of a recent hour, and only once receptions has no rows left in the first layout. Each run stages into a table of its own, and the systemd unit's name keeps a second replay from starting while one runs. On the box, as the loader user, about 45 minutes a day:

```sh
systemd-run --unit=aiscast-replay --property=EnvironmentFile=/etc/aiscast.env --property=User=aiscast \
  --property=WorkingDirectory=/var/lib/aiscast --property=Nice=10 --property=IOSchedulingClass=idle \
  /opt/aiscast/aiscast replay -clickhouse clickhouse://loader@127.0.0.1:9000/aiscast -fetch -archive /var/lib/aiscast/replay \
  -from 2026-09-01 -to 2026-09-02 -dry-run
journalctl -fu aiscast-replay
```

A track covers up to 366 days per request and pages back by moving `to`. Without an `interval` it is simplified by shape ([simplify.go](simplify.go)): the server reads the range at full detail, drops positions implying an impossible speed, and keeps the positions that hold the path. A range that starts in the last 48 hours reads every position through the `positions` view, grouped to whole seconds when more than 50,000 would match; further back it reads `positions_1m`, grouped to whole minutes past 50,000 rows, a year to 11 minutes. Each stretch between silences, over 30 minutes in the view or an hour in `positions_1m`, keeps its two ends. Inside it, positions are dropped nearest first, by how far each lies from where the line between its neighbors puts the vessel at its time, until every one left lies more than 15 m off: a stay at the dock collapses to its arrival and departure, a stop on a straight leg stays, and a trip draws the same path at any range that fits the limit. Past the limit the tolerance rises until the track fits, and the answer says `truncated`; it says so too when the range holds more than 50,000 positions and the oldest are not read. The answer carries `simplified`, `tolerance_m`, `breaks`, the positions that start a stretch after a silence, and as `interval` the resolution it read at. A GPX file has a segment per stretch. With an `interval`, a range that starts in the last 48 hours reads the `positions` view, thinned to its step in the query, whatever the step, so a recent track thins every position. Further back, a step under a minute over a range up to 31 days reads every position through the view, at any age, and a step of a minute or more reads `positions_1m` grouped by the step. A range too long for every position, such as `interval=0` over more than 31 days, is thinned to a minute, and the answer reports that interval. `interval=0` asks for every position, and the newest `limit` positions are returned when more match. The answer's `from` and `to` say what was covered. The limit is capped by tier: 1,000 anonymous or with a personal token, 5,000 for feeder and above. An anonymous or personal `interval` that reaches past the last 48 hours is rounded up to whole minutes, so it reads `positions_1m`: the limit bounds the answer, not the copies a step under a minute would group through the `positions` view. Positions whose stamps disagree with their fixes, implying an impossible speed, are left out. `/metrics` reports copies written and dropped, and write failures and seconds.

## Historical archives

Government AIS archives load into ClickHouse as receptions that arrived late, from a feed the network does not run ([history.go](history.go)). Each is its own `source` and `station`, with its own license and credit, and never reaches the stream. Once ClickHouse is attached, and every six hours after, the server lists each archive's files, one UTC day each, and loads every day from its start that `history_loads` has not recorded with the file's current ETag, newest first. Loads wait while `receptions` still holds rows in its first layout, until `aiscast convert-receptions` and `aiscast clickhouse-cleanup` have run. ClickHouse downloads, decompresses, and parses each file itself, into a staging table, and the server then reads the staged day a vessel at a time, beside the day's transmissions from other sources, and writes through the live writer's own insert:

- A row is kept when its MMSI is a ship's (a maritime identification digit of 2 to 7), its time falls in the file's day, and it has a position: latitude 91, longitude 181, and (0, 0) are not positions. Exact repeats of a row collapse to one.
- A row at the position of a transmission another source delivered, within 4 wire units (about 0.75 m), the nearest in time within 5 minutes, is a copy of it, as a rebuilt live copy is: AISHub's stamps run tens of seconds off. It takes that transmission's name, its verdict on moving, and its `implausible` flag, and is not accepted. MarineCadastre's five decimal places put a row up to 3 wire units from the wire value.
- A row that jumps from both of its neighbors, more than 10 NM at more than 120 kn, is kept with `implausible` set. A lone spike jumps from both; a good row beside one jumps from only one. Runs of bad rows pass, and despike removes them from a drawn track.
- Every other row is its own transmission, accepted, so `positions_1m` takes it, named with a byte free in its millisecond and judged moving or still by the vessel's anchor, which starts afresh each day.
- A row arrives when it loaded, clamped to `recv_delay`'s 24.8 days, so the `positions` view keeps serving the live copies of a transmission the network also heard.
- Names, call signs, IMO numbers, ship types, dimensions, and draughts fold into `vessel_statics`, per vessel and source.

Loads connect as `CLICKHOUSE_LOADER_URL`, the `loader` user in [users.d/loader.xml](deploy/rootfs/etc/clickhouse-server/users.d/loader.xml), whose settings profile keeps every load query within 1.5 GB and two threads at a lower priority, so loading never takes what the live writer needs: ClickHouse refusing the writer for 10 minutes would drop live positions. A file loaded before, or a load that failed partway, has its day's rows from that archive deleted first, so no row is ever there twice, and its day of `positions_1m` is rebuilt after. `history_loads` keeps, per file, the rows read, those without a place, the repeats, those kept, matched, and implausible.

MarineCadastre (`MARINECADASTRE`) is the U.S. Coast Guard's Nationwide AIS, published by NOAA and BOEM as one zstd CSV a day on Azure, about two months behind and a quarter at a time: the U.S. coasts, the Great Lakes, Hawaii, Puerto Rico, and Canadian waters within reach of U.S. receivers; Alaska ends on 2021-03-28. Each vessel has at most one position a minute. A day is about 240 MB to download, 10 million rows, and 150 MB in ClickHouse; loading one takes under three minutes, most of it the download.

DMA (`DMA`) is the Danish Maritime Authority's archive: every report its shore stations heard in Danish waters, the Skagerrak, the Kattegat, and the western Baltic, stamped to the second, in a public S3 bucket three days behind. Each day is a zipped CSV, and ClickHouse reads the CSV inside the zip with `s3()`. Days before 2024-03 come a month to a zip, and ClickHouse reads one day's CSV out of it without downloading the rest. The CSV has 22 columns before 2019 and 26 after, and the load reads columns by name, so both load the same. Only class A and B transponders are vessels, so base stations, aids to navigation, and SAR aircraft are counted as read and not kept. Several stations hear most reports, so over a third of a day's rows repeat another exactly. A day is about 725 MB to download, 3.8 GB of CSV, and 21 million rows, of which about 11 million are kept, at about 100 MB in ClickHouse. Parsing and writing a day takes under a minute on a laptop, so the download sets the pace. In Danish waters the live network is almost all AISHub. On 2026-10-01, about a quarter of the kept rows matched a transmission the network already held, and 90% of AISHub's transmissions in the minutes DMA also heard a vessel gained a DMA copy. Almost all of the rest were reports DMA did not hear: under 2% of the unmatched ones that were moving had a DMA row within 8 wire units, about 1.5 m.

`/metrics` reports each archive's newest day loaded, 0 until one has, files loaded and failed, checks that failed before any file, such as a listing that stalled, and rows.

## Access log

Every HTTP request is one JSON line in the access log, written when the response finishes, so a stream is logged once, when it closes. A stream still open when the server stops is not logged. Lines go into hourly gzip files under `ACCESS_DIR` and upload to `access/v1/YYYY/MM/DD/HH.gz` in `ACCESS_BUCKET`, through the same rotation and disk sweep as the archive. It is a private bucket of its own and never the archive's, because the raw archive is meant to become publicly mirrorable and R2 makes a whole bucket public at once. Its keys have the shape of raw hours, so `aiscast replay` skips `access/` by name if a copy ever lands beside the raw archive.

A line holds:

- `t`: when the response finished, UTC.
- `id`: Caddy's request id, which its own access log on the box records too.
- `method`, `route` (the mux pattern, or `other`), `path`, and `query`. The path is canonical: the route with its path values filled in only where they are plain numbers (`x` otherwise), and only the first segment of a path no route matched. The query keeps only the parameters the server reads, so a token sent under any other name is dropped. Any token left in these or in the user agent, origin, or referer is redacted. Coordinates in `around` (a search ranked from the visitor's own position) and `bbox` (the view) are rounded to 0.1°, and a tile deeper than z12 is logged as the z12 tile holding it, with the requested zoom in `z`: about 10 km either way, so a line shows where load falls without placing a home or a berth.
- `status`, `ms`, and `bytes` of body written. A WebSocket's frames bypass the writer, so a socket logs its handshake bytes only.
- `net`: the client's /24 or /48. `client`: a keyed hash of its address, from `STATION_SALT` under a label of its own, so the hash cannot be matched against UDP station ids. The key is stable, so one client's requests group across days and weeks for following abuse. Whoever holds the key can recover an address from its /24, so the lines are personal data, kept 90 days.
- `sub` and `role` of a token that verified. An anonymous request has neither.
- `ua`, `origin`, and `referer` without its query, which can carry a token.

A line never holds a token, a full address, or a precise location. The bucket deletes hours after 90 days with a lifecycle rule; without a bucket, the sweep deletes them on disk at the same age. The full address is in Caddy's log on the box for under two weeks, joined by `id` ([deploy/README.md](deploy/README.md#access-logs)). Writing a line never holds up a request. When the writer falls behind, lines are dropped and counted in `aiscast_access_dropped_total`. The files load directly into DuckDB:

```sql
SELECT route, count(*) AS n, quantile_cont(ms, 0.99) AS p99_ms, count(DISTINCT client) AS clients
FROM read_json_auto('access/v1/2026/10/02/*.gz') GROUP BY route ORDER BY n DESC;
```
